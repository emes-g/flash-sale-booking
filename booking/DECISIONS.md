## 1. 재고 정합성 및 공정성
> **쟁점: 00시 정각 대규모 트래픽 집중 시 발생하는 동시성 문제 해결 및 모든 사용자에게 선착순(FIFO) 기회 보장**

### DB 비관적 락 대신 Redis 분산 락 선택
- 트래픽 집중 시 DB 비관적 락을 사용하면 트랜잭션 대기 시간 증가로 커넥션 풀이 고갈될 위험이 커, 애플리케이션 외부의 Redis를 활용해 동시성을 제어했습니다.

### Redisson Fair Lock을 통한 공정성 보장
- 단순 분산 락이 아닌 `getFairLock()`을 채택했습니다.
- 락 획득을 위해 대기하는 스레드들을 큐(Queue)에 넣어 요청이 도달한 순서대로 락을 부여함으로써, 모든 사용자에게 동등한 기회(선착순)를 제공하도록 했습니다.

### Lock과 Transaction의 생명주기 통제 (Facade 도입 근거)
- 락을 제어하는 메서드에 `@Transactional`을 함께 걸면, 트랜잭션 커밋이 완료되기 전에 락이 먼저 풀려 동시성이 깨지는 문제가 발생합니다.
- 이에, 트랜잭션이 완전히 커밋된 이후에 락이 해제되도록 실행 순서를 엄격히 통제했습니다.

## 2. 고가용성 설계
> **00시 정각, 순간 TPS 1000 이상의 예약/결제 트래픽이 몰릴 때 DB 커넥션 풀 고갈과 I/O 병목을 방지하여 시스템 붕괴를 막는 구조 설계**

### 읽기 트래픽 방어 (DTO 기반 Redis 캐싱)
- 트래픽의 상당 부분을 차지하는 주문서 진입(`GET /checkout`) API의 병목을 없애기 위해 숙소 정보를 Redis에 캐싱(`@Cacheable`)했습니다.
- 이때, `Accommodation` 엔티티 객체를 그대로 캐싱하면 JPA 프록시 문제와 불필요한 연관관계 데이터까지 직렬화되는 오버헤드가 발생합니다.
- 이를 방지하기 위해 직렬화/역직렬화 효율이 높고 필수 데이터만 포함된 `AccommodationCacheDto` 구조로 변환하여 캐싱함으로써 메모리 사용량을 최적화하고 DB 부하를 차단했습니다.

### 쓰기 트래픽 방어 (트랜잭션과 네트워크 I/O의 물리적 분리)
- 결제 처리 로직(`PaymentService`) 전체를 `@Transactional`로 묶으면, 외부 PG사 API를 호출하고 응답을 기다리는 시간(네트워크 지연) 내내 DB 커넥션을 점유하게 되어 순식간에 커넥션 풀 고갈(Connection Pool Exhaustion) 장애로 이어집니다.
- 이를 해결하기 위해 결제 서비스 메서드에서 선언적 트랜잭션(`@Transactional`)을 제거하고 `TransactionTemplate`을 도입했습니다. 
- 외부 결제 API 호출 전후의 데이터베이스 상태 변경(결제 내역 저장, 예약 확정) 구간만 짧은 단위의 트랜잭션(Short Transaction)으로 묶어 DB 커넥션 점유 시간을 극단적으로 최소화했습니다.

## 3. 멱등성 처리 (Idempotency)
> **쟁점: 네트워크 지연에 따른 재시도나 사용자의 중복 클릭으로 인한 동일 결제 요청의 중복 처리 방지**

### Redis 기반 분산 환경 멱등성 검증
- `BookingFacade` 진입 시 `userId`와 `accommodationId`를 조합하여 생성한 고유 키를 Redis에 5초간 저장(`SET NX`)합니다.
- 해당 키가 이미 존재하여 `false`를 반환할 경우, 현재 처리 중인 요청으로 판단하고 예외를 발생시켜 중복 진입을 방지합니다.

### DB 기반 Fallback 검증
- Redis 장애 상황을 고려하여 데이터베이스를 통한 2차 검증 로직을 포함했습니다.
- 예약 생성 전, `bookingRepository`를 통해 최근 5초 이내에 동일한 사용자 및 숙소에 대한 예약 내역이 존재하는지 확인(`existsByUserIdAndAccommodationIdAndCreatedAtAfter`)하여 정합성을 유지했습니다.

## 4. 확장성 (Payment Scalability)
> **쟁점: 결제 수단 추가 시 기존 비즈니스 로직의 수정을 최소화하고 다양한 결제 방식을 수용할 수 있는 구조 설계**

### 전략 패턴(Strategy Pattern) 도입
- 결제 처리 로직을 `PaymentProcessor` 인터페이스로 추상화하고, 각 결제 수단(신용카드, Y페이, Y포인트)을 독립적인 클래스로 구현했습니다.
- 이를 통해 새로운 결제 수단이 추가되어도 `PaymentService`의 기존 코드를 변경하지 않고 신규 구현체만 추가하면 되는 OCP(Open-Closed Principle) 원칙을 준수했습니다.

### 복합 결제 및 동적 처리
- 요청에 포함된 결제 수단 리스트를 순회하며 각 구현체의 `supports` 메서드를 통해 적합한 처리기를 선택합니다.
- 이 구조를 통해 단일 결제는 물론, 서로 다른 결제 수단이 혼합된 복합 결제 요청도 비즈니스 로직의 변경 없이 유연하게 처리할 수 있도록 설계했습니다.

## 5. 장애 대응 및 예외 처리 (Resilience)
> **쟁점: Redis 서버 장애 및 외부 PG사 결제 API 통신 실패 시, 시스템 전체의 가용성을 유지하고 데이터 정합성을 복구하는 방안**

### Redis 단일 장애점(SPOF) 대응 Fallback
- 분산 락 및 멱등성 검증을 담당하는 `Redis`에 타임아웃이나 연결 장애(`RedisException`)가 발생할 경우, 컨트롤러 계층에서 이를 감지하여 DB 비관적 락(Pessimistic Lock) 기반의 결제 로직(`checkoutAndPayFallback`)으로 즉시 우회하도록 설계했습니다.
- 이를 통해 인프라 장애가 전체 서비스 다운으로 이어지지 않도록 가용성을 보장했습니다.

### 결제 실패에 따른 보상 트랜잭션(Saga Pattern)
- 결제 API 호출 구간을 DB 트랜잭션과 분리했기 때문에, 결제 통신 중 장애가 발생하면 이미 처리된 재고 차감과 예약 생성(`PENDING`) 내역을 수동으로 롤백해야 합니다.
- 예외 발생(`catch`) 시 기존 예약을 `FAILED` 상태로 변경하고, 감소한 재고를 다시 증가시키는 보상 트랜잭션(`rollbackBooking`)을 명시적으로 호출하여 최종 데이터 정합성을 맞추었습니다.

## 6. 도메인 설계: 숙소(Accommodation)와 재고(Stock) 엔티티 물리적 분리
> **쟁점: 숙소 기본 정보와 한정된 객실 재고를 단일 테이블로 관리할 것인가, 물리적으로 분리할 것인가**

### 결정 및 근거
- 단일 테이블로 관리할 경우, 00시 정각에 재고 차감을 위한 쓰기 락(`Lock`)이 점유되면 숙소 정보를 단순 조회하는 GET 요청들까지 대기 상태(Blocking)에 빠지는 병목이 발생합니다.
- 이를 해결하기 위해 조회가 빈번한 'Read-Heavy' 데이터(`Accommodation`)와 변경이 빈번한 'Write-Heavy' 데이터(`AccommodationStock`)를 분리했습니다.
- 숙소 기본 정보는 캐싱하여 락 없이 응답하고, 예약 생성 시에는 `AccommodationStock` 레코드에만 락을 집중시켜 동시성 제어와 조회 성능을 동시에 확보했습니다.
